# 内置沙箱支付设计

日期：2026-08-24

## 目标

为当前模块化单体增加可测试的支付闭环：创建支付单、沙箱回调验签、回调幂等、超时关闭和订单状态转换。实现不依赖第三方支付平台，后续可替换为真实渠道适配器。

## 数据模型

新增 Flyway 迁移 `payment_records` 表：

- `id`：自增主键。
- `payment_no`：唯一支付单号。
- `order_id`：订单 ID，建立索引并唯一约束一笔订单的有效支付单。
- `buyer_id`：买家 ID，防止跨用户支付。
- `amount`：支付金额，使用 `DECIMAL(10,2)`。
- `channel`：当前固定为 `SANDBOX`。
- `status`：`PENDING`、`PAID`、`FAILED`、`CLOSED`。
- `expires_at`、`paid_at`、`callback_count`、`last_callback_at`、创建和更新时间。

支付单金额必须与订单金额一致。数据库保存支付状态和审计时间，不保存银行卡、密码或其他敏感支付信息。

## API 与状态流转

### 创建支付单

`POST /api/orders/{orderId}/payment`

- 仅已认证买家可调用，并且订单必须属于当前买家。
- 仅 `PENDING_PAYMENT` 订单可创建支付单。
- 存在未过期 `PENDING` 支付单时返回原记录，保证重复点击不产生多个有效支付单。
- 已支付、已关闭或订单处于其他状态时返回明确业务错误。
- 返回支付单号、订单号、金额、渠道、状态和过期时间。

### 沙箱回调

`POST /api/payments/sandbox/callback`

请求包含 `paymentNo`、`orderNo`、`amount`、`result`、`timestamp`、`signature`。签名为 HMAC-SHA256，签名原文按固定字段顺序拼接；密钥通过 `AGROMALL_SANDBOX_PAYMENT_SECRET` 配置，生产 profile 必须显式提供。

- 验签失败、时间戳超出允许窗口、支付单不存在、订单号不匹配或金额不匹配均拒绝。
- `SUCCESS` 仅允许 `PENDING -> PAID`，并使用条件更新把订单从 `PENDING_PAYMENT` 改为 `PENDING_SHIPMENT`。
- `FAILURE` 仅把 `PENDING` 支付单改为 `FAILED`，不改变订单状态。
- 对已 `PAID` 的重复成功回调返回相同成功结果；对已 `FAILED` 或 `CLOSED` 的回调返回幂等结果，不重复扣库存或恢复库存。
- 每次合法回调递增次数并记录最后时间；不记录原始敏感请求体。

### 超时关闭

后台定时任务扫描过期 `PENDING` 支付单：先条件更新为 `CLOSED`，再只取消仍为 `PENDING_PAYMENT` 的订单。普通订单恢复已扣库存；秒杀订单调用现有秒杀释放逻辑，避免重复补偿。已经支付或订单已被用户取消的记录不再处理。

## 前端边界

待支付订单的“去支付”入口调用创建支付单接口，展示支付单号、金额、过期时间和“模拟支付成功/失败”按钮。按钮调用沙箱回调接口，仅用于开发验收；页面明确标注为沙箱，不展示真实支付渠道名称。回调成功后刷新订单并显示待发货状态。

## 错误处理与安全

- 所有接口沿用 `ApiResponse<T>` 和全局异常处理器。
- 买家只能创建和查看自己的支付单，回调接口不依赖用户 JWT，但必须通过签名和字段校验。
- 支付金额使用 `BigDecimal`，禁止浮点比较。
- 支付密钥不得写入仓库；开发可从 `.env` 注入，生产缺失时启动失败。
- 回调和超时处理必须使用数据库条件更新，确保并发请求不会重复转换订单或恢复库存。

## 测试与验收

- 后端：支付表迁移、创建权限和状态、重复创建复用、验签失败、金额不一致、成功/失败回调、重复回调、过期关闭、普通订单库存恢复和秒杀订单释放。
- 前端：支付入口只对待支付订单显示，创建支付单展示真实返回数据，成功/失败按钮和错误状态可见。
- 运行后端全量测试、前端全量测试、生产构建，并完成一次浏览器沙箱支付验收。

## 明确不做

- 不接入支付宝、微信或其他第三方平台。
- 不保存真实支付凭证、银行卡信息或回调原文。
- 不实现退款、分账、优惠券、支付对账和多币种。
- 不拆分支付微服务；当前实现留在模块化单体内。
