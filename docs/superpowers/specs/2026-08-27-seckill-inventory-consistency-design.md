# 秒杀库存一致性与并发压测设计

日期：2026-08-27

## 目标

将秒杀商品与普通商品库存明确隔离，修复 Redis 活动库存与商品数据库库存分叉问题，并提供可重复运行的真实 Redis 并发测试。

## 商品隔离

- 商品新增 `sale_mode`：`NORMAL`、`SECKILL_ONLY`，默认 `NORMAL`。
- 秒杀活动只能绑定 `SECKILL_ONLY` 且处于 `ON_SALE` 的商品。
- 普通商品列表、商品详情公开接口、购物车加入和普通结算过滤 `SECKILL_ONLY`。
- 秒杀专用商品库存仅由秒杀流程消费，不参加普通订单库存扣减。

## 秒杀库存流程

1. 发布活动时校验专用商品库存，按活动库存预热 Redis。
2. 抢购请求通过 Redis Lua 原子检查库存和一人一单资格。
3. Lua 成功后，在数据库事务中条件扣减专用商品库存、创建秒杀订单、订单明细和秒杀关联记录。
4. 数据库事务失败时，使用一个 Lua 补偿脚本同时增加 Redis 库存并移除用户资格；不得使用两条独立 Redis 命令。
5. 用户取消或超时关闭时，仅在订单状态从 `PENDING_PAYMENT` 成功转为 `CANCELLED` 后执行一次补偿。
6. 对账测试验证：商品库存减少量等于成功秒杀订单数，Redis 剩余库存等于活动库存减成功预留数加已补偿数。

## 并发压测

- 提供 k6 脚本或同等轻量脚本，支持配置活动 ID、并发用户数、库存量、请求地址和 JWT 模板。
- 测试前使用测试 profile、独立数据库和 Redis 前缀，预热固定库存。
- 断言 HTTP 成功数不超过库存、同一用户最多成功一次、无库存时返回售罄、数据库订单数与 Redis 成功预留数一致。
- 输出吞吐量、P95/P99 延迟、错误率、Redis CPU/内存和 MySQL 连接池指标。
- 先做 10/50/100 并发基线，再逐步增加并发；不在生产环境直接运行破坏性压测。

## 工具建议

- 推荐 k6：脚本化、安装轻量、适合 HTTP 并发和 CI；Windows 可用 `winget install k6.k6` 或 Docker 运行。
- 可选 Apache JMeter：需要图形化配置、团队已有 JMeter 经验或要更复杂的场景时使用。
- 必需依赖：Docker Desktop（运行 MySQL/Redis）、JDK 21、Node.js（启动前端，可选）、Redis CLI 或 RedisInsight（观察 key 和库存）。
- 可选监控：Prometheus + Grafana；首次压测可先用 k6 输出和 Spring 日志，不必先部署监控栈。

## 是否需要 RabbitMQ

当前不需要。现有秒杀流程是 Redis 原子预扣后同步创建数据库订单，RabbitMQ 不会自动解决库存一致性，反而会增加消息重复、幂等、失败重试和补偿复杂度。只有在明确要把“创建订单”改为异步削峰、引入订单事件或多个服务解耦时，才评估 RabbitMQ；那会是单独的架构变更，不属于本阶段。

## 验收

- 数据库迁移、普通商品过滤、秒杀专用商品约束和权限测试通过。
- Redis 补偿 Lua 测试通过。
- k6 并发基线在测试环境通过，成功订单、商品库存和 Redis 库存三者可对账。
- 后端、前端全量测试和前端生产构建通过。

## 明确不做

- 不引入 RabbitMQ、Kafka 或新的消息中间件。
- 不把秒杀拆成独立微服务。
- 不实现多件限购、分布式锁替代 Lua 或生产环境压测。
