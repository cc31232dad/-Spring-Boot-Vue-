# 基于 Spring Boot 与 Vue 的助农商城设计规格

## 1. 项目定位

本项目是一个面向消费者、农户和平台管理员的农户入驻型助农商城。系统采用前后端分离的模块化单体架构，围绕农产品交易建立完整业务闭环，并以农产品溯源、助农专区和 Redis 秒杀作为主要特色。

项目从空白仓库自主建设，参考成熟开源商城的通用业务思路，但不直接复制或换皮现有项目。通用商城能力按照本项目的数据模型和模块边界实现；农户入驻、农产品溯源、助农秒杀等领域功能独立设计。

## 2. 目标与验收标准

项目完成时应满足以下条件：

- 消费者、农户、管理员三类角色权限隔离正确；
- 农户能够提交入驻申请，管理员能够完成审核；
- 农户发布的商品经审核后才能上架销售；
- 普通商品能够完成购物车、下单、支付、发货和收货流程；
- 商品能够关联溯源批次及生产、检测、采收记录；
- 助农专区能够展示滞销、临期或平台补贴农产品；
- 秒杀并发测试中不超卖、同一用户不重复购买；
- 支付宝沙箱能够完成支付，并正确处理异步通知与主动查单；
- 待支付订单超时后能够取消并恢复相应库存；
- 核心业务具备自动化测试，项目具备可复现的部署文档；
- Git 提交记录能够体现分阶段开发过程。

## 3. 范围边界

第一版不包含以下功能：

- Spring Cloud 微服务及分布式事务；
- 真实资金交易、平台抽佣、分账与农户提现；
- 消息队列异步下单；
- 直播带货、即时聊天和小程序；
- 推荐算法；
- 动态秒杀路径、复杂验证码与集群部署；
- 复杂退款渠道接口。

上述能力可在论文未来展望中说明，但不影响第一版验收。

## 4. 技术架构

### 4.1 总体架构

- 后端：Spring Boot 3、Spring Security、JWT、MyBatis-Plus；
- 前端：Vue 3、Vite、Pinia、Vue Router、Element Plus；
- 数据存储：MySQL；
- 缓存与秒杀：Redis、Lua；
- 支付：支付宝沙箱，模拟支付作为本地演示备用通道；
- 文件：开发阶段本地存储，后续可切换 MinIO；
- 部署：Nginx、Spring Boot Jar、MySQL、Redis；
- 架构形态：前后端分离的模块化单体。

### 4.2 后端模块

后端按业务领域组织，而不是仅按 Controller、Service、Mapper 分层堆放：

- `auth`：注册、登录、JWT 与权限；
- `user`：消费者资料与地址；
- `farmer`：农户入驻、资料和审核；
- `product`：分类、商品、图片和库存；
- `trace`：溯源批次与溯源记录；
- `cart`：购物车；
- `order`：订单、明细、发货与状态转换；
- `payment`：支付宝沙箱支付、回调与查单；
- `seckill`：秒杀活动、资格与库存；
- `assistance`：助农专区；
- `review`：评价与收藏；
- `admin`：运营、审核与日志。

## 5. 角色与功能

### 5.1 消费者

- 注册、登录和个人资料管理；
- 浏览首页、分类、助农专区和秒杀活动；
- 按名称、产地、分类和价格搜索商品；
- 查看商品详情、农户信息、评价和溯源记录；
- 管理购物车、收藏和收货地址；
- 创建普通订单或秒杀订单；
- 使用支付宝沙箱支付并查询支付结果；
- 查看订单、确认收货和发表评价。

### 5.2 农户

普通用户提交申请并通过审核后，同时拥有 `USER` 与 `FARMER` 角色，可以经营商品，也可以购买其他农户的商品。

- 提交入驻资料和证明材料；
- 维护农户故事、产地介绍和联系方式；
- 发布、编辑、上下架商品并维护库存；
- 维护播种、施肥、检测、采收等溯源记录；
- 处理订单、填写物流信息并确认发货；
- 提交秒杀活动申请；
- 查看订单量、销售额和库存预警。

### 5.3 管理员

- 查看用户、农户、订单、销售额和助农数据看板；
- 审核农户入驻、商品、秒杀活动和溯源信息；
- 管理用户、分类、订单、轮播图、公告和售后争议；
- 开启或结束秒杀活动并同步库存；
- 查看登录、审核和关键业务操作日志。

## 6. 权限与安全

系统采用 RBAC 模型，核心角色为 `USER`、`FARMER`、`ADMIN`。前端根据角色展示菜单，后端使用 Spring Security 对所有受保护接口执行真实授权校验。

- 密码使用 BCrypt 哈希；
- JWT 采用短期访问令牌；
- 上传文件校验类型、大小并生成随机文件名；
- 支付密钥通过环境变量或本地私有配置提供，不提交 Git；
- 关键业务记录用户编号、订单号和请求编号；
- 接口不返回 SQL、调用栈、密钥或内部文件路径。

## 7. 数据模型

### 7.1 核心表

- 用户权限：`user`、`role`、`user_role`；
- 地址：`user_address`；
- 农户：`farmer_application`、`farmer_profile`；
- 商品：`product_category`、`product`、`product_image`；
- 溯源：`trace_batch`、`trace_record`；
- 购物：`cart_item`、`favorite`；
- 订单：`orders`、`order_item`；
- 支付：`payment_record`；
- 秒杀：`seckill_activity`、`seckill_order`；
- 评价：`product_review`；
- 运营：`banner`、`announcement`；
- 审计：`operation_log`。

业务实体按需包含创建时间、更新时间、逻辑删除和乐观锁版本字段，关联表不机械添加无意义字段。

### 7.2 核心关系

- 一个农户可以发布多个商品，一个商品只属于一个农户；
- 一个商品属于一个分类，可以拥有多张图片和多个溯源批次；
- 一个溯源批次可以拥有多条生产或检测记录；
- 一个订单包含多个订单明细，但只包含同一农户的商品；
- 跨农户购物车结算时，后端按农户自动拆分订单；
- 普通订单与秒杀订单共用订单主表和明细表，通过 `order_type` 区分；
- 一笔订单可以对应多条支付尝试记录。

## 8. 状态模型

### 8.1 商品

商品审核状态和上下架状态分开保存。典型流程为：草稿、待审核、审核通过或驳回；审核通过后可以上架或下架。

### 8.2 订单

订单状态包括：

- `PENDING_PAYMENT`：待支付；
- `PAID`：已支付、待发货；
- `SHIPPED`：已发货；
- `COMPLETED`：已完成；
- `CANCELLED`：已取消；
- `REFUNDING`：退款中；
- `REFUNDED`：已退款。

后端统一校验状态转换：创建后进入待支付，支付回调成功后进入已支付，农户只能发货已支付订单，用户确认收货后进入已完成。待支付订单十五分钟后自动取消。已发货订单不能直接取消。

## 9. 普通订单与库存

普通下单在数据库本地事务中完成：

1. 校验商品、上下架状态和购买数量；
2. 使用乐观锁扣减库存；
3. 按农户拆分并创建订单；
4. 创建订单明细并保存商品快照；
5. 删除本次结算的购物车条目；
6. 提交事务。

订单价格以服务端读取的数据为准，不能信任前端金额。每次创建请求携带业务请求号，用于防止重复提交。

## 10. 支付宝沙箱支付

创建待支付订单后，用户可以发起支付宝沙箱支付。`payment_record` 保存订单号、平台交易号、金额、渠道、状态、请求时间、回调时间和通知摘要。

异步通知处理步骤：

1. 验证支付宝签名；
2. 验证应用及商户信息；
3. 验证订单号和金额；
4. 判断支付记录与订单是否已经处理；
5. 在同一本地事务中更新支付记录和订单状态；
6. 对重复通知直接返回成功。

系统同时提供主动查单能力，避免浏览器同步跳转结果被当作最终支付依据。模拟支付只作为无法连接沙箱时的本地演示兜底，并通过配置显式启用。

## 11. Redis 秒杀

秒杀用于临期、滞销或平台补贴农产品。第一版每名用户每场活动限购一件。

`seckill_activity` 保存商品、秒杀价、活动总库存、限购数、起止时间和状态。活动开始前将库存预热到 `seckill:stock:{activityId}`，已抢购用户记录在 `seckill:buyers:{activityId}`。

抢购流程：

1. 校验用户、活动状态和时间；
2. Lua 脚本原子检查库存、检查一人一单、扣减库存并写入用户资格；
3. 数据库事务创建 `SECKILL` 类型订单；
4. 创建失败时补偿 Redis 库存和购买资格；
5. 成功后进入支付宝沙箱支付；
6. 十五分钟未支付时取消订单、恢复库存并释放购买资格；
7. 活动结束后核对 Redis 与数据库结果。

第一版同步创建订单，不引入消息队列。若压力测试证明数据库落单是主要瓶颈，再将消息队列作为后续扩展。

## 12. API 约定

接口统一使用 REST 风格，路径按领域与角色划分：

- `/api/auth/**`：认证；
- `/api/products/**`：公开商品查询；
- `/api/cart/**`：购物车；
- `/api/orders/**`：订单；
- `/api/payments/**`：支付；
- `/api/seckill/**`：秒杀；
- `/api/traces/**`：溯源；
- `/api/farmer/**`：农户经营功能；
- `/api/admin/**`：管理员功能。

统一响应包含 `code`、`message`、`data`。分页结果包含 `records`、`total`、`page`、`size`。金额在 Java 中使用 `BigDecimal`，数据库使用 `DECIMAL`。

## 13. 异常处理

全局异常处理覆盖参数错误、未登录、权限不足、资源不存在、库存不足、重复请求、支付异常和系统异常。业务冲突返回稳定错误码，前端据此显示可理解提示。

库存、订单与支付遵循以下一致性原则：

- 普通库存使用数据库事务和乐观锁；
- 秒杀资格使用 Redis Lua 原子操作；
- 秒杀落库失败立即补偿 Redis；
- 支付记录和订单状态在一个本地事务更新；
- 定时任务关闭超时订单并恢复对应库存；
- 支付通知和创建订单接口均实现幂等。

## 14. 测试策略

### 14.1 单元测试

覆盖金额计算、订单状态转换、库存规则和秒杀资格判断。

### 14.2 后端集成测试

覆盖登录权限、农户和商品审核、普通下单、重复请求、库存不足与事务回滚。

### 14.3 支付测试

覆盖沙箱支付成功、失败、取消、重复回调、金额不匹配和主动查单。

### 14.4 秒杀压力测试

使用 JMeter 模拟并发请求，记录吞吐量、平均响应时间、错误率和最终库存，验证不超卖、一人一单、订单总量不超过活动库存，以及 Redis 与数据库最终一致。

## 15. 参考项目策略

优先研究 `newbee-mall` 的商品、购物车和订单思路，参考 `RuoYi-Vue` 的权限与后台设计，并按许可证要求保留必要的版权及归属说明。项目不直接继承无关企业级能力，不照搬页面、命名或数据结构。

参考代码进入项目之前必须回答三个问题：该代码解决什么业务问题；是否符合本规格；开发者能否在答辩中解释其原理。不能回答时不引入。

## 16. 实施原则

- 先完成可运行的核心交易闭环，再增加溯源和秒杀；
- 每个阶段包含数据库变更、后端、前端、测试和文档；
- 使用小步 Git 提交，禁止一次性导入整个参考项目；
- 每个模块完成后保留演示数据、接口测试结果和论文截图素材；
- 不以中间件数量衡量项目质量，以业务完整性、正确性和可解释性为准。
