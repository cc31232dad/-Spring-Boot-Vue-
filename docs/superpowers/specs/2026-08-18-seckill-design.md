# Phase 4 Redis 秒杀设计

## 目标

为农产品商城增加限时秒杀能力，保证高并发抢购下库存不超卖、同一用户在同一活动中最多成功一次，并在数据库落单失败或订单超时取消时恢复 Redis 侧库存与购买资格。

## 范围

- 管理员创建、发布、结束秒杀活动。
- 活动包含商品、秒杀价、总库存、每人限购数量、开始时间和结束时间。
- 活动开始前将库存预热到 `seckill:stock:{activityId}`。
- 抢购接口使用 Redis Lua 脚本原子完成活动时间校验、库存校验、用户限购校验、库存扣减和用户资格记录。
- 抢购成功后同步创建待支付秒杀订单；数据库失败时补偿 Redis。
- 待支付秒杀订单取消或超时后恢复 Redis 库存和用户资格。
- 增加后端 API、服务和并发行为测试，以及最小可用的前端活动与抢购页面。

## Redis 协议

- `seckill:stock:{activityId}`：字符串整数，表示可抢库存。
- `seckill:buyers:{activityId}`：Set，成员为用户 ID，表示已成功获得资格的用户。
- Lua 脚本返回明确结果码：成功、库存不足、重复购买、活动未开始、活动已结束。
- 补偿操作只在数据库事务未成功提交时执行，并使用 Lua 或等价原子操作同时恢复库存与移除用户资格。

## 数据流

1. 管理员发布活动，服务校验商品和时间，并写入数据库、预热 Redis 库存。
2. 登录用户调用抢购接口。
3. 服务校验活动存在及状态后执行 Lua 脚本。
4. Lua 成功后，在本地事务中创建 `SECKILL` 类型订单和订单明细，订单初始状态为待支付。
5. 落单失败时补偿 Redis；成功时返回订单视图。
6. 用户取消或定时任务处理超时订单时，恢复 Redis 库存并释放购买资格。

## 一致性与错误处理

- Redis Lua 保证抢购资格判断和扣减库存的原子性。
- 数据库事务保证秒杀订单和订单明细同时提交或回滚。
- Redis 预扣成功但数据库落单失败必须补偿，否则会造成库存泄漏。
- 统一使用现有 `ApiResponse` 和 `BusinessException` 错误协议。
- 普通订单流程保持不变，秒杀订单通过 `order_type` 区分。

## 测试验收

- 活动创建、发布、结束和权限测试。
- 秒杀成功、活动未开始、已结束、库存不足和重复购买测试。
- 数据库落单失败后的 Redis 补偿测试。
- 并发请求下成功订单数不超过活动库存，单个用户最多一个成功订单。
- 秒杀订单取消或超时后库存和购买资格恢复。
- 前端测试和生产构建通过。
