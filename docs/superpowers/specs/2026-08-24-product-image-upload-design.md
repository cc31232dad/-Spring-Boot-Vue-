# 商品图片上传与后续开发路线设计

更新时间：2026-08-24

## 目标

降低农户发布商品的操作成本，让农户直接从电脑文件或手机相册选择图片，不需要寻找或填写图片链接。同时按照业务风险和依赖关系，规划后续核心功能的实施顺序。

## 当前范围

第一阶段只实现：

- 桌面端拖拽图片
- 桌面端点击选择图片
- 移动端从相册选择图片
- 本地预览、替换和删除
- 后端上传、校验、安全命名和持久化
- 上传成功后自动写入现有 `imageUrl` 字段

明确不实现：

- 移动端拍照上传
- 与豆包等生图平台的 API 绑定
- 图片二进制存入数据库
- 多图详情管理（作为后续独立迭代）

## 用户流程

```text
农户打开商品表单
    -> 点击上传区域或拖入图片
    -> 移动端从相册选择
    -> 浏览器显示预览
    -> 上传服务校验并保存
    -> 返回图片地址
    -> 商品提交时保存 imageUrl
```

原有图片链接能力可保留为低优先级备用入口，但不再作为主流程。

## 技术设计

### 前端

- `input[type=file]` 使用 `accept="image/jpeg,image/png,image/webp"`。
- 桌面端监听 dragenter、dragover、dragleave、drop，并提供拖入高亮。
- 移动端只展示相册选择，不提供 camera capture 属性。
- 上传前显示本地预览和文件信息。
- 上传中禁用商品提交，失败时保留表单内容并允许重试。

### 后端

- 新增认证商品图片上传接口，仅允许已登录农户上传。
- 限制 JPG、PNG、WEBP，单文件不超过 5 MB。
- 同时校验扩展名、MIME 和文件内容，使用随机安全文件名。
- 第一阶段写入 `backend/uploads/products`，通过静态资源映射访问。
- Docker 将上传目录挂载为 volume，避免容器重建丢失文件。
- 数据库继续保存 URL，不保存图片二进制；后续可替换为 MinIO/OSS。

## 后续开发优先级

1. 商品图片上传闭环：本设计对应的第一阶段。
2. 环境与数据隔离：开发、测试、生产配置和验收数据分离。
3. 沙箱支付：支付单、支付状态、创建支付、回调验签、幂等和超时关闭。
4. 秒杀可靠性：商品库存冻结、Redis/MySQL 对账、幂等、补偿和并发压测。
5. 物流能力：发货单号、状态同步和买家查询。
6. 评价能力：评分、文字、图片、重复评价限制和农户回复。
7. 售后能力：退款、售后申请、审核和状态流转。
8. 管理与安全：统计聚合、管理员账号分级、JWT 撤销、审计日志和监控。
9. 体验优化：移动端拍照上传、图片裁剪、多图详情、历史图片复用。

## 验收标准

- 农户可以在桌面端拖拽或点击选择图片。
- 农户可以在移动端从相册选择图片。
- 不需要农户填写图片 URL。
- 非图片、超过 5 MB 或伪造 MIME 的文件被拒绝。
- 上传失败不会丢失商品表单内容。
- 商品审核、买家详情和商城列表可以正常展示上传图片。
- 后端上传接口有权限、校验和异常测试。
- 前端有选择、预览、失败和提交禁用测试。
- `mvn test`、前端测试和生产构建通过。

## 明确的延期项

移动端拍照上传属于体验优化，不阻塞图片上传第一阶段，也不阻塞支付、库存一致性等核心业务功能。
